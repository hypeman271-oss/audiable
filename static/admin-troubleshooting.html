Admin troubleshooting — tenant keys

Things to check when the Tester keys section doesn't appear in Settings, or when minting / listing / revoking a key isn't working. Admin-only. Bookmark this page — /admin-troubleshooting.html.

The short version

The Tester keys form in Settings only appears when the server confirms your bearer is the admin. That's three things in a chain:

  1. The server is running v221.tenants code (so the /api/admin/whoami endpoint exists).
  2. Your browser is running the new frontend build (so the Tester keys HTML section is in the DOM).
  3. The bearer your browser is sending matches the server's NARRATIVE_KEY exactly (so the server replies is_admin: true).

If any one of those is wrong, the section stays hidden. The checks below walk through each.

Step 1 — Is the server up to date?

The /api/admin/* endpoints only exist after the v221.tenants code has shipped. Confirm with a curl from PowerShell: 

$key = "<paste your NARRATIVE_KEY>"
$base = "https://narrative-alpha.fly.dev"

curl.exe -H "X-Narrative-Key: $key" "$base/api/admin/whoami"

What the response means

  • {"tenant_key":"...","is_admin":true,"tenant_label":"admin"} → server is up to date AND your key matches. Skip to Step 2 — the problem is on the browser side.
  • {"detail":"Not Found"} or an HTML 404 page → the server hasn't been redeployed yet. Run fly deploy from E:\audiable. Wait for the new build to roll, then re-curl.
  • {"detail":"invalid X-Narrative-Key"} → the bearer your curl sent doesn't match the env var. Skip to Step 3.
  • {"is_admin":false,"tenant_label":"alice"} (or some other label) → you're authed as a tester, not the admin. That happens when the bearer you pasted is a tester bearer, not NARRATIVE_KEY. Switch the bearer to the env-var value.

Step 2 — Is your browser running the new frontend?

The service worker caches index.html aggressively. Even after you redeploy, the browser will keep serving yesterday's HTML — which doesn't have the Tester keys section — until the new SW activates.

Force the SW to update (desktop Chrome / Edge)

  1. Open the app.
  2. Press F12 → Application tab → left sidebar Service Workers.
  3. Tick Update on reload.
  4. Close DevTools. Press Ctrl + Shift + R (hard refresh).
  5. Open Settings. You should now see the Schedule maintenance section AND below it, the Tester keys section.

Force the SW to update (Firefox)

  1. Ctrl + Shift + Del → tick Cookies and Site Data + Cached Web Content → time range Last hour → Clear.
  2. Close and reopen the tab.

Force the SW to update (mobile PWA)

The PWA stays alive even when you close the visible window.

  1. iOS: Settings → Safari → Advanced → Website Data → search "narrative" → swipe to delete. Reopen the PWA from the home screen.
  2. Android: Settings → Apps → Narrative → Storage → Clear cache (NOT Clear storage — that wipes your local library too). Reopen.
Every time I ship a frontend change I bump CACHE in static/sw.js. That triggers the SW to refetch the shell next time the user opens the app. But it still takes one reload after the first visit because the SW activates in the background — the first page load is served from the old cache, the new cache populates, and the next reload sees the new shell. So if you redeployed seconds ago, refresh twice.

Step 3 — Does your bearer match NARRATIVE_KEY?

The middleware does a constant-time compare between the X-Narrative-Key header and the NARRATIVE_KEY env var. They have to match byte-for-byte — a trailing newline, a stray space, or a different copy of the key all fail the compare.

Check what the server has

fly secrets list

That'll show the secret names (not values). Confirm NARRATIVE_KEY is in the list. To see the actual value the server is using, you have to look in the Fly dashboard secrets UI, or shell in and read the env var: 

fly ssh console -C 'printenv NARRATIVE_KEY'

Check what your browser is sending

Open DevTools → Network → reload the app → click any request to /api/* → look at the request headers. Find X-Narrative-Key. Compare it character-by-character to what the server has. Common culprits:

  • Trailing newline from a copy-paste. PowerShell's Read-Host appends one; fly secrets set NARRATIVE_KEY=$(...) inherits it.
  • Wrong tester key. You typed your alpha- tester bearer into the prompt on this device instead of the admin one. Open Settings → clear local storage's narrative.apiKey (or in browser console: localStorage.removeItem('narrative.apiKey')), reload, paste the admin key.
  • Multi-line paste. Some clients append CRLF to clipboard contents; the prompt accepts it as-is.

Fix a key mismatch

If the env var is wrong: fly secrets set NARRATIVE_KEY=value then fly deploy (or fly machine restart — secrets aren't reloaded on SIGHUP).

If the browser side is wrong: clear narrative.apiKey from localStorage, reload, re-paste at the prompt.

Using the Tester keys form (once it's visible)

Minting a key

  1. Settings → scroll to Tester keys.
  2. Type a label that helps you identify the tester later: alice — alice@gmail.com works.
  3. Click Mint key. A green box appears with the raw bearer (looks like narrative-xxxx-xxxx-xxxx-xxxx).
  4. Click Copy. Paste it somewhere safe immediately — once you close Settings, the key is no longer re-shown in the UI. It still exists in /data/tenants.json on the server, but the API listing endpoint redacts it.
The raw key is only shown once. If you click away before copying it, your only recovery is to fly ssh console and grep /data/tenants.json for the label — clunky and feels risky. Just copy it immediately.

Sharing the key with a tester

Currently manual: paste the key + the app URL into Signal / email / SMS / paper. There's no in-app delivery mechanism. The tester pastes the key into the X-Narrative-Key prompt on first load.

Revoking a key

  1. Settings → Tester keys → Existing testers list.
  2. Click Revoke next to the row. Confirm.
  3. That bearer stops authenticating immediately. The tester's library rows stay in the DB but become unreachable. To fully purge their data would need a manual SQL step on the volume — not implemented yet.

Verifying isolation between two testers

Before you hand out keys to multiple real testers, sanity- check that they really are isolated. Mint two keys yourself:

  1. Mint test1 and test2 via the Settings form.
  2. Open the app in two different browser profiles (or one normal window + one private window). Paste test1 in the first, test2 in the second.
  3. In the test1 window, make a clip. Save it. Open Settings → Sync → On.
  4. In the test2 window, open Settings → Sync → On. The library should be empty. Tester 1's clip should not appear.
  5. Make a different clip in the test2 window. Sanity-check again from the test1 side — only test1's clip.

After confirming, revoke both test keys. They're not needed anymore.

If nothing here helps

Check fly logs for a stack trace at the moment you opened Settings or clicked Mint. The most useful filters: 

# Tail the latest minute
fly logs

# Search for migration / DB issues
fly logs | findstr "library_db"

# Search for auth issues
fly logs | findstr "X-Narrative-Key"

Send the relevant log line and the curl output from Step 1.
